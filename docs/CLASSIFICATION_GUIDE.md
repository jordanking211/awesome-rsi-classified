# 如何区分自改进 Agent 的技术路线：修改对象、训练边界与递归性

**中文** | [English](CLASSIFICATION_GUIDE.en.md) | [完整分类索引](../README.md)

本指南解释 Awesome RSI Classified 的分类判断方法。**先确认系统实际写回了什么，再判断谁被训练、更新是否被后续过程使用，以及效果有没有独立证据。** 九类修改对象是实现分析视角，不是能力等级，也不是统一的 RSI 定义。

本文整理既有条目的分类证据；不新增性能复现，也不更新各项目的源码核查日期。具体版本和核查范围以链接条目为准。

<a id="decision"></a>
## 分类时需要回答哪些问题？

**分类单位是一个方法的具体实现路径，而不是整个项目名称。** 同一框架可能同时支持提示优化、模型训练和代码生成；不能把其中一个优化器的结论推广到整个框架。

1. **比较更新前后留下的产物。** 是指令、经验、可调用技能、工作流、事件 hook、Agent 源码、任务程序、权重，还是研究产物？仅生成一段反思文字，不足以证明系统发生了持久更新。
2. **查找写回与加载位置。** 更新写入哪个文件、变量、数据库或检查点？下一轮在哪里读入？保存文件和实际使用文件是两件事。
3. **确定主对象并保留次对象。** 以所查优化路径的主要对象归类；多个对象共同更新时，在条目中明确，不把耦合关系删掉。
4. **分开记录训练与推理。** 哪个模型或控制器进行了参数更新？调用固定模型生成代码，不代表训练了该模型。
5. **最后判断递归性和效果。** 递归机制、跨任务泛化、旧任务回归和运行成本各自需要证据，不能由主分类替代。

九类定义与边界见[分类表](../README.md#taxonomy)，完整方法及源码依据见[方法总览](../README.md#overview)。

<a id="prompt-memory-skill"></a>
## 提示词、记忆和技能有什么区别？

**关键区别在于更新内容在后续系统中的作用，文件扩展名并不能决定分类。** Markdown 可以装指令、经验或技能；代码也可以是可复用技能、Agent 实现或单个任务答案。

| 判定问题 | 更接近的对象 | 可核查例子及边界 |
| --- | --- | --- |
| 是否替换模块的指令或示例？ | 提示词 | [MIPROv2](../README.md#miprov2) 搜索并赋值 instructions / demos；结论仅覆盖所查优化器 |
| 是否保存经历、反思并在后续检索或注入？ | 记忆 | [Reflexion](../README.md#reflexion) 的所查路径更新反思并加入后续提示 |
| 是否积累可调用、可复用的操作方法？ | 技能 | [Voyager](../README.md#voyager) 保存 JavaScript 技能及描述，并检索技能代码 |

原始资料：[MIPROv2 论文](https://arxiv.org/abs/2406.11695)、[Reflexion 论文](https://arxiv.org/abs/2303.11366)、[Voyager 论文](https://arxiv.org/abs/2305.16291)。表中链接条目提供对应固定提交的源码位置。

**容易误判的例子：** [GEPA](../README.md#gepa) 的候选包含文本组件，适配器决定这些文本被解释为提示、技能或代码。不能仅凭“文本优化”就断言所有 GEPA 应用都只修改提示词，也不能仅凭“技能”名称就认定存在可执行技能库。[来源：GEPA 原论文](https://arxiv.org/abs/2507.19457)及上述实现条目。

<a id="agent-versus-program"></a>
## 修改 Agent 与演化任务程序有什么区别？

**修改 Agent 改变执行任务或产生改进的系统；演化任务程序改变该系统提交的一个任务解。** 两者都可能生成 Python 文件、使用测试并保存版本，因此要追踪候选代码被谁加载、承担什么职责。

| 对比维度 | Agent 自身代码修改 | 目标任务程序演化 |
| --- | --- | --- |
| 主要对象 | Agent / harness / 改进器实现 | 解决目标任务的函数或程序 |
| 后续作用 | 成为执行或改进系统的一部分 | 作为候选解接受评测或部署 |
| 本索引实例 | [SICA](../README.md#sica)：当前 coding agent 的代码库 | [OpenEvolve](../README.md#openevolve)：被优化程序及候选种群 |
| 不能直接推出 | 修改一定提升下一轮改进能力 | 求解程序变好等于改进器变好 |

原始来源：[SICA 论文](https://arxiv.org/abs/2504.15228)、[OpenEvolve 仓库](https://github.com/algorithmicsuperintelligence/openevolve)。本索引的对应条目记录具体源码核查范围。

**反例：** 一个固定搜索器不断生成更快的排序函数，能够构成程序优化闭环，但如果搜索器本身没有更新，就不能仅凭循环次数认定其改进机制发生了递归改进。这是分类示例，不是性能实验结果。

<a id="training"></a>
## 不训练权重是否等于没有学习？

**模型权重冻结，只能说明相关模型参数没有更新；系统仍可能通过提示、记忆、技能或代码改变后续行为。** 这些改变能否带来学习意义上的泛化，需要另行评测。

同时应避免相反的误判：系统没有微调基础模型，不代表所有组件都不训练。工作流中的图参数、辅助模型或专家可以单独拟合。记录时分别列出“修改的产物”“训练的组件”“训练与部署阶段”，不要只填写一个全系统的“是否训练”。参见[工作流分类](../README.md#workflow)及[权重与联合更新分类](../README.md#weights)。

<a id="recursion"></a>
## 什么时候才能讨论递归自改进？

**在本索引的严格审视口径下，需要追踪改进机制是否改变，以及改变后的机制是否参与后续改进。** 这是一项分析条件，并非声称学界只有一个定义。

- **任务答案变好：** 支持该任务上的改进，不能单独证明系统得到持久更新。
- **系统产物更新且后续使用：** 支持存在更新闭环；仍需识别更新的是任务解还是改进系统。
- **改进机制更新并参与下一轮：** 支持进一步检查递归结构，但持续能力收益、泛化和安全性仍需实验。

不要把这三种证据解释为一个通用能力排行榜。完整讨论及方法入口见[递归边界](../README.md#recursive-boundary)。

<a id="evidence"></a>
## 如何记录与引用分类结论？

一条可复核结论应包含：**方法与实现版本 → 主修改对象 → 次对象 → 写回位置 → 后续使用位置 → 训练组件 → 核查范围 → 未验证事项。** 未定位某个环节时明确写“未核验”，不要用项目宣传语填空。

例如：“所查 Reflexion 路径更新并注入反思文本，因此归入记忆；此分类不构成性能复现结论。”这是带范围的实现分类，比“Reflexion 已经实现通用 RSI”更符合已有证据。
